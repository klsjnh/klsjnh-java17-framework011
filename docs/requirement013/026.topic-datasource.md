## 013.关键路径

### 013.1 表驱动注册表（本期技术核心）

现有 `DynamicDataSourceRegistryImpl` 的 `configs` 只从 `krt.ci011` 装载。本期改为**表为运行时真源**：

```text
启动 / reloadRegistry 调用
  → repository.findAllEnabled()            # july_datasource where dr='0' and status='1'
  → 逐条转 ConnectionInfo（driverClass 空则按 dbType 取 DatabaseTypes011 内置默认）
  → registry.reloadAll(List<ConnectionInfo>)
       ├── 先构建 nextMap（null / 空 dsCode 跳过），再整体替换 configs
       ├── Pass 1：快照内的 dsCode — 物理目标未变则 reused++ 保留旧池；
       │          变了且已建池则 DynamicDataSource011.remove + pools.close
       ├── Pass 2：旧声明集里快照中已消失的 dsCode（删 / 停用）→ 同样关池
       └── 回报 ReloadResult { enabled, registered, reused, closed, failed } 并落一条日志
```

**池的创建仍是懒加载**（`DataSourcePools011.get` 的 `computeIfAbsent`）—— `reloadAll` 只声明配置与关旧池，**不预建新池**。这是本项目优于老项目之处（老项目 `buildRegisteredPool` 内 `pool.init()` + `initialSize 2`，启动即连，一个库配置错就拖慢启动）。

**池保留判据**（落在 `ConnectionInfo.sameTarget(other)`）：`dsCode` 存在 **且** `jdbcUrl` / `username` / `password` / `dbType` 四值全等 → 复用；否则关旧建新（下次调用时懒建）。避免"改个 remark 就断所有连接"。

**两个 pass 不重叠**：Pass 1 处理"在快照里但变了"，Pass 2 处理"不在快照里了"，同一个 dsCode 不会被关两次。

### 013.2 测试连接（本期明确口径）

用户定案的四项参数全部落地：

| 参数 | 值 | 说明 |
|------|-----|------|
| `initialSize` | 0 | 不预热 |
| `maxActive` | 1 | 单连接探测 |
| `maxWait` | 10000 | 10s 超时 |
| 注册表 | **不碰** | 探测完即 `pool.close()`，注册表零副作用 |

```text
testConnection(vo)
  → vo 含 id        → 取库中配置（password 留空则用库里存的那份；支持重测已保存数据源）
  → vo 不含 id      → 由 vo 字段构造草稿 ConnectionInfo（支持未保存即测，老项目同款体验）
  → DataSourceProbe011.probe(info)          # 实现 domain 的 DataSourceProbePort
       ├── pool = buildForProbe(info)      # maxActive 1 / maxWait 10s / testOnBorrow
       ├── conn = pool.getConnection()
       ├── meta.getDatabaseProductName() / getDatabaseProductVersion()
       └── finally: pool.close()           # 探测池必关（Druid 持真实 socket）
  → 返回 ProbeResult { success, message, databaseProduct, databaseVersion }
  → HTTP 恒 200：success=false 表示"探测动作成功，只是目标不通"，由调用方读 success 分支
```

**与既有 `DynamicDataSourceRegistryImpl.testConnection(ConnectionInfo)` 的关系**：该方法保留（端口既有契约），其实现内部同样走 `pools.buildForProbe`，但**不返回产品信息**。本期的 `DataSourceProbe011` 是**新增的**、供管理端点用的探测件，返回更丰富的 `ProbeResult`，且两个入口都遵守"不回灌注册表"。

### 013.3 密码出站脱敏

收口点唯一：**`JulyDatasourceConverter.toVo()`**（web 层）。

- 域聚合 `JulyDatasource` 持有 `password`（业务必需：建池要用）；
- 转换到 `JulyDatasourceVo011` 时**不复制该字段**，`Vo011` 内**不定义 `password`**（不是置空，是根本没这个字段——从类型层面杜绝泄露）；
- `testConnection` 的入参 VO 可带 `password`（探测需要），但它不是响应类型。

### 013.4 请求前缀与包结构


**为什么是顶层 `datasource` 而非塞进 `system011`**：`system011` 的语义是「系统管理」（菜单 / 用户 / 角色 / 配置）；数据源管理是独立的**数据源内核 / 管理**能力，与业务建模解耦（后者已迁至低代码产品项目）。URL 前缀 `/klsjnh/datasource/**` 与包名对齐。

**Swagger 分组**（`SpringDocConfig011` 一命名空间一组）：新增 `datasourceGroupedOpenApi()` —— group `datasource` / displayName `数据源011` / `pathsToMatch("/klsjnh/datasource/**")`。**Controller 的 `@Tag` 与表注释统一口径**：`数据源011 - 数据源管理`（与 DDL `COMMENT='数据源011 - 数据源管理'` 一字不差）。

> 与 `system011` 的差异：现有 system011 各 `@Tag` 写作「系统管理 - 配置管理」（不带 `011`）。新域一律带域号，**不改存量**（存量改动属独立任务，需单独授权）。

## 015.DDL 与契约增量

### 015.1 DDL（新落 `docs/sql/july_datasource.sql`）

按 `docs/sql/july_config.sql` 的**列顺序规范**：`id → 业务字段 → status → 审计四列 → dr`。

与老项目 DDL 的修正：
1. 审计四列改 `BasePo` 口径（`create_time` / `update_time` / `create_by` / `update_by`）；
2. `id` 用 `VARCHAR(33)`（对齐 `base-entity-columns.sql` 的 32 位 UUID + 余量）；
3. 补 `KEY idx_ds_code_status (ds_code, status)`（注册表 reload 的查询模式）；
4. 补 `sort_order INT NOT NULL DEFAULT 9999`（2026-09-15：管理列表手工排序，PO 改继承 `BasePo011`；insert/update 可维护，列表按 `sort_order ASC, id ASC`）。

### 015.2 API 契约

**无信封 / 状态码增量** —— 全部复用 `013.api-contract.md` 现有六键信封与 `HttpCodeEnum011`。错误码映射：

| 场景 | 状态码 |
|------|--------|
| `dsCode` 重复 / 保留字 / 未知 `dbType` / `jdbcUrl` 非 `jdbc:` 开头 | 400 |
| `getById` / `getByCode` 不存在 | 404 |
| 停用的 `dsCode` 被路由 | 400 |
| 探测失败（连不上 / 认证失败） | **200 + `data.success=false`**（探测动作本身成功执行，结果在载荷内） |

> 最后一条是有意设计：`testConnection` 的语义是"**执行一次探测**"，探测动作成功即 HTTP 成功，连通与否是业务结果。老项目同款口径。

### 015.3 无 Flyway / Liquibase

本项目 DDL 走 `docs/sql/*.sql` 手工执行（现有 `july_config.sql` 等同一口径），本期不引入 migration 工具。

## 017.与老项目的取舍（哪些不照搬）

| 老项目做法 | 本期决策 | 原因 |
|------------|----------|------|
| `DynamicDataSourceUtil` 硬编码 `if ("mysql"…oracle…sqlserver)` | ❌ 不照搬 | `DatabaseTypes011` 字符串常量是内置驱动类名真源（2026-09-19 起替代枚举） |
| 池 `setFilters("stat,wall,log4j2")` | ❌ 不照搬 | 对业务库强加 wall 过滤，跨库 DDL / 多语句场景易误伤（现有实现已刻意不加） |
| `buildRegisteredPool` 内 `pool.init()` + `initialSize 2` | ❌ 不照搬 | 启动即连，配置错一个库拖慢启动；本期维持懒加载 |
| `reloadAll` 时全量关旧建新 | ⚠️ 改造 | 改为"配置未变则保留旧池"，避免无关改动断连 |
| 密码明文随查询回吐 | ❌ 不照搬 | 类型层面剔除字段（§013.3） |
| 列名 `pass_word` | ❌ 不照搬 | **违约命名**（单词内部拆下划线）；改 `password`，对齐 `july_user.password` 与 `ConnectionInfo.password`，规约见 [016.coding-standards §7](../016.coding-standards.md) |
| `batchLogicDelete` 命名 | ❌ 不照搬 | 违反现行门禁"动词打头"（§6.3），改 `logicDeleteBatch` |
| `testConnection` 临时池不清 | ⚠️ 改造 | 补 `finally` 关池（§013.2） |
| `DbType`（`final class` + 静态常量） | ❌ 不照搬 | 已有 `DatabaseTypes011` 字符串常量；方言分页为开放 SPI（`SqlDialectPort011` + `SqlDialect011` 注册表，2026-09-19） |
| `OperatorContext` 手工 set/clear | ❌ 不照搬 | 本项目已定案走 request attribute + `AuditMetaObjectHandler`（见 [031 持久化中心 · 013 §019](../infrastructure011/031.persistence-center/013.topic-architecture.md)） |
| `july_sql` / `july_model` 三表齐发 | ➖ 不做 | 由低代码产品项目承接（两表合并为一张 `july_business_modeling`）；本域只做数据源 |

**保留借鉴**：`reloadAll` 的三计数日志、草稿态测试连接、`dsCode` 保留字 `master` 校验、`ExternalDatasourceOps` 的"临时池探测"思路。

## 021.E2E 验收清单（Step 5 用）

1. `insert` 建一条 mysql 数据源 → 200
2. 同名 `dsCode` 再 insert → 400
3. `dsCode` 用 `master` → 400
4. `dbType` 传 `bogus` → 400
5. `jdbcUrl` 不以 `jdbc:` 开头 → 400
6. `update` 改 `remark` → 200，且**既有池不断**（同 dsCode 后续路由成功；reload 日志 `reused=1`）
7. `update` 改 `jdbcUrl` → 200，旧池被关，下次路由重连（`closed=1`）
8. `update` 时 `password` 留空 → 库里密码不变
9. `getById` → **响应无 `password` 字段**（类型层无该字段）
10. `testConnection` 传**未保存**的草稿配置（连不上）→ **200** + `data.success=false`
11. `testConnection` 传已保存的 `id`（能连）→ 200 + `data.success=true` + `databaseProduct`
12. `status=0` 停用后 `reloadRegistry` → 该 dsCode 从注册表消失
13. `logicDelete` → 后续 `getById` 404；注册表内该 dsCode 消失
14. `logicDeleteBatch` 部分成功 → `BatchDeleteResultVo011` 逐条回报（整批只 reload 一次）
