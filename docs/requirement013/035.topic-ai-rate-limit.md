# 035.ai-rate-limit — AI 中心 Provider 限流与并发（P1）

> 阶段：**requirement013（详细设计 · 对接代码）**
> 关联：[AI 中心 011 设计](../../infrastructure011/017.ai-center/011.topic-design.md) · [013 架构](../../infrastructure011/017.ai-center/013.topic-architecture.md) · [015 使用](../../infrastructure011/017.ai-center/015.topic-usage.md)
> 状态：**已实现**（in-process 默认实现 + 可替换 SPI）

## 011.问题

厂商 API 常见两类限制：

- **速率**：如 StepFun 的某些接口要求 3 秒一次；
- **并发**：同一 key 同时在途请求数有限。

此前 AI 中心只有超时；`HttpUtil011` 仅把上游 429 归类为 `rate limited`，**不排队、不限流、不重试**。业务侧各自 sleep 会：

- 无法阻止多业务同时打爆；
- 行为不统一（阻塞/报错/重试各不相同）；
- 流式请求的并发额度无法释放。

## 013.决策

| 层 | 归属 | 内容 |
|---|---|---|
| Provider 速率 / 并发 | **框架** | `AiRateLimiterPort`；默认 in-process；按 provider / provider+api / provider+model 维度 |
| 业务配额 | 应用 | 租户/用户/功能/成本配额，优先级队列 |
| 分布式额度 | 应用或网关 | Redis / 网关；框架只定义 SPI，默认实现是单 JVM |
| 重试 | 应用（可选框架后置） | 429/5xx 退避；默认不自动重试，避免放大成本 |

## 015.配置

```yaml
krt:
  ai-center:
    rate-limit:
      enabled: true
      defaults:                      # 未单独配置的 provider 用默认值（0 = 不限）
        min-interval-ms: 0
        max-concurrent: 0
        max-wait-ms: 10000
        scope: provider
      providers:
        stepfun:
          min-interval-ms: 3000
          max-concurrent: 2
          max-wait-ms: 10000
          scope: provider            # provider / api / model
```

## 017.行为

```
acquire(provider, api, model)
  ├─ 未启用 / 两个维度都为 0 → no-op permit
  ├─ 并发：Semaphore.tryAcquire(max-wait-ms)
  │    └─ 超时 → 429（TOO_MANY_REQUESTS）
  └─ 间隔：synchronized 预订下一个窗口（nextAllowed）
       ├─ 需要等待且超过 max-wait-ms → 429
       └─ 否则 parkNanos 等待后返回 permit
```

- **permit 必须关闭**：普通调用用 try-with-resources；流式调用挂在 `Stream.onClose`，HTTP SSE 消费端 `try (stream)` 关闭；
- **等待上限**：`max-wait-ms` 内排队，超时 429；`0` 表示不等待（立即失败）；
- **scope**：`provider`（默认）/ `api`（provider+apiKey）/ `model`（provider+apiKey+model）；
- **429 契约**：`HttpCodeEnum011.TOO_MANY_REQUESTS(429)`，`BusinessException.tooManyRequests(...)`。

## 019.接入点

| 能力 | 位置 |
|---|---|
| 推理同步 / 流式 | `AiInferenceUseCase.chat` / `stream`（stream 用 `onClose` 释放） |
| 图片 | `AiImageUseCase.generate` |
| TTS / ASR | `AiTtsUseCase.synthesize` / `AiAsrUseCase.recognize` |
| 厂商文件 | `AiFileUseCase` 的 upload / get / list / delete / content |

## 021.边界

- 默认实现 **单 JVM**：多实例部署时每个实例各有一份额度，不等于全局 3 秒一次；
- 需要全局额度时，应用提供 `AiRateLimiterPort` bean（Redis / 网关），`AiRateLimitConfig011` 的 `@ConditionalOnMissingBean` 会让默认实现退让；
- 框架不引入 Redis/Resilience4j 依赖；
- 上游 429 仍按错误返回（可读 message），不在框架内默认重试。

## 023.测试

- `LocalAiRateLimiter011Test`：最小间隔等待、并发上限 429、无配置 no-op；
- `KrtAiConfig011Test`：`krt.ai-center.rate-limit.providers.*` 绑定；
- 各用例单测构造器注入 no-op limiter，行为不回归。

## 025.风险

| 风险 | 处理 |
|---|---|
| 阻塞等待占用请求线程 | `max-wait-ms` 限制；高并发场景用应用侧队列 |
| 流式未关闭导致并发泄漏 | 文档 + `onClose`；SSE controller 已 `try (stream)` |
| 多实例额度不共享 | 明确单 JVM 语义，提供 SPI |
| 配置 provider code 拼写错误 | 未命中走 defaults；启动日志可后续补校验 |
