## 011.机制（本次规划的核心，先说结论）

### 011.1 新机制一句话

```text
july_datasource  →  july_business_modeling  →  lowcode011  →  低代码操作表
   （已有）              （本方案新建）           （接收方）      （运行时能力）
```

### 011.4 表结构演进对照

| 维度 | 老项目（f016） | 本项目（本方案） | 变更性质 |
|------|---------------|------------------|----------|
| 表数量 | `july_sql` + `july_model` + `july_metadata` = **3 张** | `july_business_modeling` = **1 张** | 合并 |
| SQL 与建模 | 分居两表，`july_model.sql_code` 外键指 `july_sql.code` | **同表同行** | 合并 |
| 数据源归属 | `july_sql` 有值，`july_model` 冗余一份 | **只有一份** `data_source_code` | 去冗余 |
| 落库形态 | `july_model.field_data` 存 JSON，其余拆散列 | **除公共列外，产物整体存一列 JSON** | **本次修正** |

| 建表能力 | `DdlBuilder.buildCreateTable` + 改名备份 + 迁移交集 | **本期不做建表**（见 §013.3） | 降级 |
| 双版本号 | `version011`（草稿）+ `version013`（发布） | **都不做**（JSON 内含即够，见 §013.2） | 收缩 |

### 011.5 为什么合并成一张表就够

老项目拆两张的**唯一动因**是「多条建模复用同一条 SQL」—— 但生产实践里：

- 建模与 SQL **一对一**（每个低代码对象一条取数 SQL），复用的抽象没被用上；
- 拆表带来的是 `sql_code` 外键一致性、`data_source_code` 双份同步、两表各自的 `status` **三处可能互相矛盾**；
- 合并后一条建模 = 一条 SQL = 一个数据源 = 一个对象，**没有跨表不变量要维护**。

**代价（需承认）**：若有「同一 SQL 被多个建模复用」的真实场景，合并后 SQL 文本会重复存储。
判据：`sql_content` 是 `TEXT` 列，重复存储的成本远低于跨表一致性的维护成本；后续要做 SQL 复用，
可另立「SQL 片段库」而不是把建模表拆开。

### 013.3 「发布建物理表」的三阶段口径（**待用户定案**）

用户答「交低代码操作表」，故本方案按**降级**规划，但把三阶段讲清楚：

| 阶段 | 内容 | 本期 |
|------|------|------|
| **A. 只出定义** | 建模产物 = JSON，不在目标库做任何 DDL | ✅ 本期 |
| **B. 交 lowcode 建表** | lowcode011 读产物 → 生成 DDL → 在目标库执行 | ⏸ 待 lowcode 域就绪 |
| **C. 本模块代为建表** | 老项目做法（`DdlBuilder` + 备份 + 迁移） | ❌ **不建议**，见下 |

**为什么 C 不建议**（老项目实际踩的坑）：

1. **不可逆**：老表改名备份后建新表，一旦迁移中途失败，回滚逻辑不在同一事务里（DDL 隐式提交），
   线上半成品表 + 备份表共存，人要手救；
2. **判交集难**：迁移只迁「新旧列名交集」，改过名的列数据直接丢，而"改字段名"是最常见的建模动作；
3. **多数据源放大**：`july_datasource` 支持 4 种库，DDL 方言差异（`AUTO_INCREMENT` / `IDENTITY` /
   `SERIAL`、`TEXT` 长度语义）要在 `DdlBuilder` 里全部分叉 —— 那是一整个独立工程；
4. **权限**：业务库账号通常**没有 DDL 权限**，建表必然失败，最后变成"要么给 DDL 权限（安全面扩大），
   要么 DBA 手工执行（自动化就没意义了）"。

**结论建议**：A 用于本期；到 B 时**只生成 DDL 脚本交人/DBA 执行**（不自动执行），
把"执行"留在人手里。

> **✅ 用户第 7 项定案：「不做」** —— 本期**不涉及**建表/发布能力（`publish` 端点不做）。
> 上述三阶段仅为**远期参考**，Step 1–4 不依赖它。

> **✅ 用户第 3 项预告**：后期要做「**抽取同步数据到本地库**」（建表之后 / 指定 SQL 两形态），
> 见 §013.1.1。该能力依赖"本地库"落点定义，**本期不做**。

## 015.表结构（DDL，新落 `docs/sql/july_business_modeling.sql`）

### 015.1 DDL 草案

按 `docs/sql/july_datasource.sql` 的**列顺序规范**：`id → 业务字段 → status → 审计四列 → dr`。

```sql
-- ============================================================
-- july_business_modeling — 数据服务011 - 业务建模
-- 列顺序规范：id → 业务字段 → status → 审计四列 → dr
-- 设计：docs/requirement011/033.topic-business-modeling.md
-- 方案：docs/requirement013/033.topic-business-modeling.md
-- 边界：合并老项目 july_sql + july_model；产物 = MetaData011 + FieldInfo011 的 JSON；
--       本表不做物理建表，产物交 lowcode011 域
-- ============================================================

CREATE TABLE IF NOT EXISTS july_business_modeling (
    id               VARCHAR(33)   NOT NULL                COMMENT '主键',
    model_code       VARCHAR(60)   NOT NULL                COMMENT '建模编码（全局唯一，不可变）',
    model_name       VARCHAR(100)  NOT NULL                COMMENT '建模名称',
    object_name      VARCHAR(60)   NOT NULL                COMMENT '低代码对象名（产物 MetaData011.objectName，全局唯一）',
    data_source_code VARCHAR(60)   NOT NULL                COMMENT '数据源编码（挂 july_datasource.ds_code）',
    sql_content      TEXT          NULL                    COMMENT '取数 SQL（探针推断 / 执行 / 分页执行共用，须以 SELECT 开头）',
    model_data       TEXT          NULL                    COMMENT '建模产物 JSON（metaData + fieldData 两个键，见方案 §015.2）',
    remark           VARCHAR(300)  NULL                    COMMENT '备注',
    status           VARCHAR(3)    NOT NULL DEFAULT '1'    COMMENT '状态（0 停用 / 1 启用）',
    create_by        VARCHAR(33)   NULL                    COMMENT '创建人',
    update_by        VARCHAR(33)   NULL                    COMMENT '最后修改人',
    create_time      DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建日期',
    update_time      DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '最后修改日期',
    dr               VARCHAR(3)    NOT NULL DEFAULT '0'    COMMENT '删除标记（0 正常 / 1 已删除）',
    PRIMARY KEY (id),
    UNIQUE KEY uk_model_code (model_code),
    UNIQUE KEY uk_object_name (object_name),
    KEY idx_ds_code (data_source_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='数据服务011 - 业务建模';
```

**`sql_content` 为什么是裸列**（用户定案 3 后新增）：SQL 执行 / 分页执行为一期能力，
且 `sql_content` 是**探针、执行、分页执行三个端点的共同入参来源**，需在管理面直接读写编辑
（定案 9：`sqlContent` 随出参返回）。它与 `meta_data` 的关系：
`sql_content` = **输入**（怎么取数），`model_data` = **产物**（取数结果的字段结构）。

> **两列都用 `TEXT`（2026-09-15 用户定案，取代原 `MEDIUMTEXT`）**：实际 SQL 与产物 JSON 最长约
> 3000–6000 字符，`TEXT`（64KB，utf8mb4 约合 16K 字符）已留 2–3 倍余量，`MEDIUMTEXT`（16MB）属过度设计。
> **不用 `VARCHAR`**：本表有两个大文本列，utf8mb4 最坏 4 字节/字符，会撞 InnoDB 65,535 字节行上限
> （如各 `VARCHAR(8000)` 合计 64,000 字节，再加其余列必爆）；`TEXT` 走 off-page，无此约束。

### 015.3 ⚠️ 一个必须注意的语义反转

`FieldInfo011.requiredField` 与 JSON 的 `notNull` **语义相反**：

| Java | JSON | 转换 |
|------|------|------|
| `requiredField = true`（必填） | `"notNull": true` | 同值（必填 ⇔ 非空）✅ |
| `requiredField = false`（可空） | `"notNull": false` | 同值 ✅ |

> 上表看着同值 —— **是与老项目** `FieldDefinition.nullable` **相反**，别混：
> 老项目 `nullable=true` 对应本项目 `requiredField=false`。**若照搬老项目的转换代码，这里必错。**

## 018.SQL 探针推断 + SQL 执行（本模块的技术核心）

### 018.1 探针流程

```text
probeAndInfer(dsCode, sqlContent, objectName)
  → 校验 sqlContent（§018.4 三条硬校验）      # 不过即 400
  → sql = sqlContent + 方言 LIMIT           # 取 10 行，避免大表全扫
  → BusinessModelingProbe011.probe(dsCode, sql)      # 读 ResultSetMetaData
  → columns = 由元数据推断
       ├── 列名 → fieldCode（snake_case 直接用）
       ├── JDBC 类型 → fieldType（§018.2 映射表，公共列优先命中 §018.3）
       └── 值长度采样 → length（取最大字符长度，向上取整到常用档位）
  → 把公共列（id/status/create_by/update_by/create_time/update_time/dr）按 §018.3 规则
     补进 fieldData
  → 返回 ProbeOutcome（不落库，前端可改）
```

### 018.1.1 SQL 执行（用户定案 3）

**这是本期新增的一期能力** —— 不只是"推断"，而是**真的跑 SQL 取数**。

```text
executeSql(dsCode, sql)
  → 校验 sql（§018.4 三条硬校验）        # 不过即 400
  → rows = SqlRoutingPort.selectList(dsCode, sql)      # 现有端口
  → 返回 ModelingResultVo011 { columns, rows }

executeSqlByPage(dsCode, sql, pageIndex, pageSize)
  → 校验 sql（同上，另校验 pageIndex / pageSize）
  → page = SqlRoutingPort.selectListByPage(dsCode, sql, pageIndex, pageSize)
  → 返回 PageResult011<Map<String,Object>>（含 total / rows）
```

| 项 | 口径 |
|----|------|
| 数据源 | `dsCode` 必须存在且**启用**（否则 400，与 031「停用即摘除」一致） |
| SQL 白名单 | **强制 `SELECT`**（§018.4）—— 本期只做**读**，不做 DML/DDL |
| 分页 | 复用 `SqlRoutingPort.selectListByPage`：**方言分页** + `pageSize` clamp `[10,500]` |
| 事务 | **不加 `@Transactional`** —— 跑在业务库，不参与主库事务（同 031 `testConnection` 口径） |
| 超时 | 建议加 `poolConfig` 侧 `maxWait`；慢查询防护见 §023 风险 3 |
| 结果集大小 | 非分页的 `executeSql` **已加行数上限 500**（走方言分页取 ≤500 行 + `total` 判定，超限 400）→ 见 §023 风险 1 |

> **`executeSql` 与 `probe` 的区别**：
> `probe` = 取 10 行 + **读元数据做类型推断** → 产物是 `fieldData`（建模用）；
> `executeSql` = 取全量（或分页）**只看数据** → 产物是结果集（看数用）。
> 两者**共用同一条 SQL 字段与同一套校验**。

### 018.2 类型推断映射表（已定案）

从 `ResultSetMetaData` 的 `getColumnType()`（`java.sql.Types`）推：

| `java.sql.Types` | 本项目 `fieldType` |
|------------------|-------------------|
| `VARCHAR` / `CHAR` | `string` |
| `LONGVARCHAR` / `CLOB` | `text` |
| `TINYINT` / `SMALLINT` / `INTEGER` / `BIGINT` | `int` |
| `DECIMAL` / `NUMERIC` / `FLOAT` / `DOUBLE` / `REAL` | `float` |
| `DATE` / `TIME` / `TIMESTAMP` | `date` |
| `BOOLEAN` / `BIT` | `boolean` |
| `BLOB` / `BINARY` / `VARBINARY` | `text`（兜底） |
| 其他 | `string`（兜底） |

> 右侧取值必须落在 `FieldType011` 枚举内（§015.4 的 12 值）。**推断结果永不产生枚举外的值** ——
> `TINYINT(1)` 特例见下。

### 018.3 公共列清单（本项目口径，权威来源）

| 列名 | `fieldType` | 说明 |
|------|-------------|------|
| `id` | `id` | 主键 |
| `status` | `status` | 状态 |
| `create_by` | `create_by` | 创建人 |

| `create_time` | `create_time` | 创建日期 |
| `update_time` | `update_time` | 最后修改日期 |

**✅ 已定案（用户第 4 项「对齐」）= 自动补齐**：若 `sql_content` 只查了业务列
（如 `SELECT code, data FROM july_config`），产物 `fieldData` **自动补上** `id` / `status` /
审计四列 / `dr`。理由：低代码生成器需要完整表结构才能建表、生成表单。

**补齐顺序**（对齐 `base-entity-columns.sql` 的列顺序规范）：
`id` → 业务列（按 SQL 选出顺序）→ `status` → 审计四列 → `dr`。

### 018.4 SQL 注入防护（三条硬校验）

落在 domain（纯 Java，无框架），**`probe` 与两个执行端点共用**：

1. `sql` **必须**以 `SELECT` 开头（忽略前导空白与 `(`）；
2. **禁止** `;`（多语句）；
3. **禁止**危险关键字：`INSERT` / `UPDATE` / `DELETE` / `DROP` / `TRUNCATE` / `ALTER` /
   `CREATE` / `GRANT` / `REVOKE` / `INTO OUTFILE` / `LOAD_FILE`（**共 11 个**，比老项目 20 个精简）。

**实现落点**：`ModelingSqlGuard`（domain 静态工具，无状态）——
供 `JulyBusinessModeling` 聚合根校验 `sqlContent` 时调用，以及 application 层在执行前复校验。

**不做的**：老项目"发布后 CRUD 走 `PreparedStatement` 真参数化"那一层 —— 本期没有"发布后 CRUD"。

## 023.风险点

| # | 风险 | 等级 | 对策 |
|---|------|------|------|
| 1 | **SQL 执行无行数上限** → 大表 `SELECT *` 打爆内存 | **高** | **已硬防**：`executeSql` 走方言分页取 ≤500 行 + `total` 判定，超限报 400 引导走分页端点 |
| 2 | **SQL 执行无超时** → 慢查询占满业务库连接池 | **高** | 走 `poolConfig` 的 `maxWait`；建议 application 层加查询超时；用**只读账号**跑业务库 |
| 3 | `fieldType` 推断与低代码生成器预期不符 | 中 | 已定 §015.4 12 值 + `FieldType011` 枚举真源；加探针单测覆盖各 JDBC 类型 |
| 4 | 分页端点被传 `pageSize=999999` | 中 | `SqlRoutingPort.selectListByPage` 已 **clamp `[10,500]`**（产品决定，无需额外处理） |
| 5 | JSON 与 Java 属性双向转换的口径漂移 | 中 | 全部收口 `ModelDataCodec011`，加**往返单测**（含 `notNull` 反转） |
| 6 | `data_source_code` 指向的 `dsCode` 被停用/删除后，已存建模的 SQL 执行失败 | 中 | 执行前校验 `dsCode` 存在且启用，失败给明确 400 提示（非 500） |
| 7 | 长 SQL 撑爆 `sql_content` | 低 | 用 `TEXT`（64KB，约为 6K 字符量级的 10 倍余量），覆盖实际需要 |
| 8 | `DisplayInfo011` / `ServiceInfo011` 长期孤儿 | 低 | 已裁定暂留；后续组织清理时一并处理 |

### 029.3 探针推断

15. `probe` 传草稿 SQL（不落库）→ 200 + 推断出的 `fieldData`
16. `probe` 目标库不可达 → 200 + `data.success=false`（探测动作本身成功）

18. 补齐后的顺序 = `id` → 业务列 → `status` → 审计四列 → `dr`（对齐 `base-entity-columns.sql`）

20. `id` 列 → `fieldType = id`；`create_by` 列 → `fieldType = create_by`（**专用类型值**，定案 1）
21. 各 JDBC 类型推断正确：`VARCHAR`→`string`、`INT`→`int`、`DECIMAL`→`float`、`DATETIME`→`date`、`TINYINT(1)`→`boolean`、`TEXT`→`text`
22. **推断结果全部落在 `FieldType011` 枚举内**（无枚举外值外泄）
23. 公共列名命中时走专用类型值：`create_by`（非法 `string`）、`dr` → `status`

### 029.4 SQL 执行（定案 3）

22. `executeSql`（dsCode 有效 + 合法 SELECT）→ 200 + 结果集（columns + rows）
