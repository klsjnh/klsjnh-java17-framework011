# 043.topic-multi-source-modeling（多入口建模与数据同步）

> 阶段：**requirement011（业务设计与业务要求）**。
> 愿景：**一个引擎、N 个门**。任何入口（SQL / 数据库表 / AI 提示 / 模板 JSON / 既有对象 / 建模交接 …）都收敛到**同一份模型契约**，再统一走「审核 → 发布 → 数据同步 → 运行时/开放 API」。
> 基础：[低代码体系 011](../lowcode011/011.topic-metadata011-system.md)（设计/发布/同步/模板）· [041 ai011 调用](../requirement011/041.topic-ai011-invoke.md)（AI）· [033 业务建模](033.topic-business-modeling.md)（建模交接）。
> 技术方案：[requirement013/042.topic-multi-source-modeling](../requirement013/043.topic-multi-source-modeling.md)
> **状态：提案（待评审）**。

## 011.核心命题

**入口多样，契约唯一，下游统一。** 入口只负责「把某种来源变成模型契约」；审核/发布/同步/运行时/开放 API 只有一套。

```
 SQL 文本 ┐
 数据库表 ├─► 源适配器 ─► 【模型契约 MetadataContent / MetaDTO(+source)】 ─► 审核 ─► 发布建表 ─► 数据同步 ─► 运行时/开放 API
 AI 提示  ┤        （种类=适配器，可插拔）        （唯一 schema；reconstitute 校验）
 模板 JSON┤
 既有对象 ┤
 建模交接 ┘
```

## 013.入口清单（N 个门）

| kind | 输入 | 产出字段方式 | 依赖 | 现状 |
|------|------|--------------|------|------|
| `sql` | 数据源 + SELECT | 探针推断 | 033 `probe` | ✅ 可用 |
| `table` | 数据源 + 表名（免写 SQL） | 读表结构（columns） | **新增「表结构读」** | ⏳ |
| `template` | 模板 JSON | 直接解析 | 040 `uploadTemplate011` | ✅ 可用 |
| `ai` | 自然语言需求 | AI 生成 JSON → 解析 | 041 + 提示词 + 重试 | ⏳（041 已通，编排未做） |
| `modeling` | 033 建模记录 id | `metaData+fieldData` 交接 | 033 `getModelData` | ⏳ |
| `copy` | 既有 objectName | 读模型 | 039 `load` | ✅ 可用 |
| (future) `excel` / `api` | 文件 / 接口 | 解析 | — | 预留 |

> **每个入口 = 一个源适配器**；新增入口不改下游。

## 015.统一契约

- **模型内容**：`MetadataContent`（objectName/objectType/description/businessField/packageName/routerPath + fields/displays/services）——即 [030 引擎重构](../lowcode011/030.topic-engine-refactor.md) 里那个 **shared kernel**；对外仍序列化为 MetaDTO（`fieldData/displayData/serviceData`）。
- **来源描述**：`metaData.source = { kind, dataSourceCode, table|sql|prompt|null, ... }` —— 让"再同步/再发布可复现"。
- 所有入口产出**必须过 `reconstitute`/模板校验**（基列/sid VARCHAR(33)/pk_xxx/枚举/display 绑定）。

## 017.统一管道

```
intake(kind, params) ─► MetadataContent ─► 校验/归一 ─► （可选）审核(previewDdl+plan)
                     ─► upsert(DRAFT) ─► deployObject(publish) ─► 数据同步 ─► 完成
```

- **审核**：`uploadTemplate011` 的 `{valid, errors, plan, previewDdl}` 对所有入口通用。
- **部署**：`deployObject`（首建 CREATE / 后仅 ADD COLUMN）。
- **数据同步**：见 §019（同样支持多来源）。

## 019.数据同步（同样多来源）

| 来源 | 说明 | 现状 |
|------|------|------|
| `source` 回放 | 用 `metaData.source` 的 SQL/表自动同步 | 部分（SQL 需显式传） |
| 显式 SQL | `importDataFromSql` | ✅ |
| **造数 mock** | 按 `fieldType` 生成 N 行模拟数据 | ⏳ **缺** |
| 异表直拷 | 源表 → 目标表 | ⏳ |
| AI 生成行 | AI 产 rows（演示/自开发） | ⏳ |

> 同步统一要求：**业务键 upsert（幂等）+ checkpoint（可续传）+ 写前校验**。

## 021.关键设计决策（待确认）

| # | 决策点 | 建议 |
|---|------|------|
| 1 | 契约形态 | ✅ `MetadataContent`（record，不可变）+ `source` 描述；**先定 shared kernel 归属**（见 030） |
| 2 | 源适配器 | ✅ 端口 `ModelSourcePort`，每入口一适配器；入口用 `kind` 路由 |
| 3 | 类型归一 | ✅ 每适配器把来源类型映射到 `FieldType011`（方言差异收敛在适配器） |
| 4 | AI 入口 | ✅ 提示词 = `getTemplate011._guide` + 硬规则；**校验失败回喂重试（≤N）**；产出仍须过审 |
| 5 | 去重/再入 | ✅ 同 `objectName` 再入 → diff → ALTER；`overwrite` 控制 |
| 6 | 可复现 | ✅ 必存 `source`；重同步默认用 `source` 回放 |
| 7 | 造数 | ✅ 新增 `mockData`（按类型生成，明文标注为模拟） |
| 8 | 安全 | ✅ 源只读、限流、审计；AI/表源同样不越权 |

## 023.评估（为什么这条思路对 / 难在哪）

**对**：
- **收敛成本**：下游只有一套（审核/发布/同步/运行时/开放 API），入口越多越划算。
- **可插拔**：新增入口 = 新增适配器，不动引擎（OCP）。
- **AI 不特殊**：AI 只是 `ai` 适配器，与 SQL/表同权，产出同样过审。
- **契约复用**：这正是 030 里 `MetadataContent` 作为 **published language** 的落地场景——多入口让"shared kernel 现在就该定"从观点变成刚需。

**难**：
1. **类型映射不统一**：Oracle NUMBER / MySQL DECIMAL / 达梦 / 布尔表示… 各自适配器要归一到 `FieldType011`。
2. **表结构读要分方言**（`information_schema` vs `user_tab_columns`）；MySQL 好办，Oracle/SQLServer 各一套。
3. **AI 产出不稳定**：必须"校验 + 重试 + 人工确认"三件套，不能无人值守建表。
4. **可复现**：不存 `source` 就无法"再同步"；`source` 要版本化（kind + params）。
5. **幂等与冲突**：同对象再入的 diff/ALTER 策略、业务键变更策略。
6. **权限/合规**：AI/表源都可能"越权读库"，要只读账号 + 审计 + 限流。
7. **契约归属**：多上下文共用 → 归属不定必漂（030 已提）。

## 025.分期（建议）

| 期 | 内容 |
|----|------|
| P1 | `ModelSourcePort` + `sql`/`template`/`copy` 适配器（复用现有）+ `intake` 编排 + `source` 落库 |
| P2 | `ai` 适配器（提示词 + 重试环）+ `table` 适配器（MySQL 表结构读） |
| P3 | `modeling` 交接 + 数据同步多来源（source 回放 / mock 造数 / 异表直拷）+ checkpoint |
| P4 | 方言扩展（Oracle/SQLServer 表结构读）+ 权限/限流 |
