## 011.问题（缺口）

建模时**源字段名 ↔ 目标对象字段名不一致**，缺少**系统性对照配置**。

- **场景 1（SQL 建模）** —— **已排除**（2026-09-18 用户口径）：SQL 里写别名即可做到**一一对应**，建模时只需**手动指定业务字段**（`SqlSourceAdapter` 已强制）；**不需要对照器**。
- **场景 8（已存在的表）** —— **本提案的驱动场景**：表已存在、结构固定、不便改写 SQL；需要**源列 → 目标字段映射**，以及**键列改别名 / 对象改名 / 显式指定**。
- **场景 6/7（Excel/CSV）** —— 表头 → 目标字段的对照（同属本提案范畴，另议交互）。

> 现状：`importDataFromSql` 按**列名大小写不敏感匹配**落列（别名仅在能改写 SQL 时可用）；场景 8 表达力不足。

## 015.候选方案（未裁决）

1. **字段级对照**：`JulyMetadataField` 增 `sourceColumn`（源列名），目标 = 字段 `fieldCode`；同步/导入按 `sourceColumn → fieldCode` 落列。
   - 优点：与字段同生命，模板/JSON 天然携带。
   - 缺点：改字段（尤其 042 后 record 契约）要动 schema。
2. **对象级映射表**：`metaData.source.mapping = { sourceCol: targetCode, ... }`（或独立表 `july_metadata_field_map`）。
   - 优点：不改字段契约；来源相关（同对象可多来源）。
   - 缺点：多一个家，需与 `businessField` 对齐。
3. **重命名入口**：intake 请求支持 `rename: {sourceCode: targetCode}`（场景 8 的对象/键改名）。
4. **Excel/CSV 表头映射**（场景 6/7）：表头 → 目标字段的交互式对照。

> 与 [045] 的关系：`businessField` 必须是**目标侧**字段 code；源侧键列名通过对照器映射到它。
