# 015.topic-fieldinfo（字段定义 + FieldType011 逐个详解 · 含字典字段）

> 低代码知识库 · 引擎 record：`com.klsjnh.domain.lowcode011.JulyMetadataField`（`MetadataContent.fields()` 元素）
> 枚举：`com.klsjnh.domain.lowcode011.enums.FieldType011`
> 总览：[011 metadata011 体系](011.topic-metadata011-system.md)；上级：[013 契约与数据模型](013.topic-metadata011.md)。

## 011.定位

`JulyMetadataField` 是 `MetadataContent` 契约内的**字段定义**：一个字段的编码 / 名称 / 类型 / 长度 / 必填 / 默认值 / 排序。它决定**物理表列**（DDL 生成器）、**运行时校验**、**展示绑定**与**数据同步映射**。

## 013.组成

| 字段 | 说明 | 约束 |
|------|------|------|
| `fieldCode` | 字段编码（**身份，不可变**，聚合内唯一） | 必填，≤60 |
| `fieldName` | 字段名称 | 必填，≤60 |
| `fieldType` | 字段类型（走 `FieldType011` 校验） | 必填，≤30 |
| `fieldLength` | 长度（0 表示长度无关类型） | 负数归一为 0 |
| `requiredField` | 是否必填 | boolean |
| `defaultValue` | 默认值 | 可空 |
| `sortOrder` | 排序 | INT |
| `param011` | 扩展参数（字典等；规划中） | 可空 |

- record 子类型；**不可变** —— 编辑走 `MetadataContent.replaceChildren(...)` 的 copy-on-write（重建契约）。
- `fieldType` 在契约里是 `String`，**校验收口在 `FieldType011.fromString`**（未知 code → null → 报 `unknown fieldType`）。

## 015.`FieldType011` 概览（12 个 code）

分两组：**结构列**（6，平台基列）与**业务列**（6）。

| code | label | 组 | 物理列（MySQL） | 运行时校验 |
|------|-------|----|------------------|------------|
| `id` | primary key | 结构 | `VARCHAR(33) NOT NULL` + PK | 长度 ≤33 |
| `status` | status | 结构 | `VARCHAR(3) NOT NULL` | 长度 ≤3（`dr` 共用此 code） |
| `create_by` | creator | 结构 | `VARCHAR(33)` | 长度 ≤33 |
| `update_by` | last modifier | 结构 | `VARCHAR(33)` | 长度 ≤33 |
| `create_time` | creation time | 结构 | `DATETIME NOT NULL` | 日期格式 |
| `update_time` | last update time | 结构 | `DATETIME NOT NULL` | 日期格式 |
| `string` | string | 业务 | `VARCHAR(length)`（0/超限→255，上限 2000） | 长度 ≤ length |
| `int` | integer | 业务 | `INT` | 整数 |
| `float` | decimal | 业务 | `DECIMAL(18,4)` | 小数 |
| `date` | date time | 业务 | `DATETIME` | 日期格式 |
| `boolean` | boolean | 业务 | `TINYINT(1)` | `true/false/0/1` |
| `text` | long text | 业务 | `TEXT` | 不限长 |

> 枚举 API：`getCode()` / `getLabel()` / `fromString(raw)`（大小写不敏感、未知返回 null）/ `isKnown(raw)`。
> `dr` 没有独立 code —— **有意共用 `status`**（两者都是 `VARCHAR(3)` 技术位）。

## 016.结构列逐个

### 16.1 `id` — 主键
- **物理列**：`VARCHAR(33) NOT NULL`，并作为 `PRIMARY KEY`。
- **生成**：DDL 生成器取 `fieldType=id` 的列作主键；若字段里**没有 id**，自动补一列 `id VARCHAR(33)` 并设主键。
- **运行时/同步**：insert 未提供时补 **32 位 hex** 随机串（`UUID` 去横线）。
- **示例**：`0000f1bd247e4060b2c205f268d6dc84`。
- **注意**：它是**代理主键**，不要承载业务；业务唯一性由 `businessField`（如 `sid`）负责。

### 16.2 `status` — 状态/启用位（`dr` 共用）
- **物理列**：`VARCHAR(3) NOT NULL DEFAULT '1'`。
- **平台语义**：`0` 停用 / `1` 启用；`dr` 用同一 code：`0` 正常 / `1` 已删除（逻辑删除，MyBatis-Plus `@TableLogic`）。
- **运行时/同步**：insert 未给时补 `status='1'`、`dr='0'`。
- **注意（B 口径）**：若把业务状态映射到平台 `status`（导入 SQL 带 `status`），会覆盖启用位 —— admin 启停与同步互相覆盖，属已知取舍。

### 16.3 `create_by` — 创建人
- **物理列**：`VARCHAR(33)`（可空）。
- **填充**：审计切面（`AuditMetaObjectHandler`）在 INSERT 时从请求操作者自动写入。
- **运行时**：必填校验**不强制**（属平台管理列）；未给留空。

### 16.4 `update_by` — 最后修改人
- **物理列**：`VARCHAR(33)`（可空）。
- **填充**：审计切面在 INSERT / UPDATE 时写入。
- 与 `create_by` 同口径。

### 16.5 `create_time` — 创建时间
- **物理列**：`DATETIME NOT NULL`，DB 默认 `CURRENT_TIMESTAMP`。
- **填充**：审计切面（INSERT）；数据同步 / 运行时若缺失补 `now`。
- **校验**：日期格式（epoch 毫秒或 `yyyy-MM-dd[ HH:mm[:ss[.SSS]]]`）。

### 16.6 `update_time` — 最后修改时间
- **物理列**：`DATETIME NOT NULL`，`ON UPDATE CURRENT_TIMESTAMP`。
- **填充**：审计切面（INSERT / UPDATE）；缺失补 `now`。

## 017.业务列逐个

### 17.1 `string` — 变长字符串
- **物理列**：`VARCHAR(length)`；`length ∈ (0, 2000]` 才生效，否则回落 `VARCHAR(255)`。
- **校验**：长度 ≤ `fieldLength`（`fieldLength>0` 时）。
- **示例**：`"100082"`、`"李新海"`。
- **前端**：`input` / `textarea`（短文本）。
- **注意**：`sid` 业务唯一键与 `pk_*` 外键列**一律固定 `string(33)`**（归一）。

### 17.2 `int` — 整数
- **物理列**：`INT`。
- **校验**：`Long.parseLong` 可解析（整数串）。
- **示例**：`1`、`100255`。
- **前端**：`InputNumber`（step 1）。
- **注意**：`INT` 有范围（±21 亿）；更大用 `string` 或 `float`。

### 17.3 `float` — 小数
- **物理列**：`DECIMAL(18,4)`。
- **校验**：`BigDecimal` 可解析。
- **示例**：`683.0000`、`1384.5`。
- **前端**：`InputNumber`（按业务定精度/步长）。
- **注意**：固定 **4 位小数**，金额/比率要评估精度（超 4 位会被截断）；Oracle `NUMBER` 探测默认推断为 `float`。

### 17.4 `date` — 日期时间
- **物理列**：`DATETIME`。
- **校验**：epoch 毫秒，或 `yyyy-MM-dd` / `yyyy-MM-dd HH:mm[:ss[.SSS]]`（也接受 `T` 分隔）。
- **示例**：`2026-09-17T18:27:42`、`2026-09-17 18:27:42`。
- **前端**：`DatePicker` + 时间格式化。
- **注意**：解析按 JVM 默认时区（`systemDefault`）；跨时区要统一。

### 17.5 `boolean` — 布尔
- **物理列**：`TINYINT(1)`。
- **校验**：`true` / `false` / `0` / `1`。
- **示例**：`true`、`1`。
- **前端**：`Switch`。
- **注意**：写入建议用 `0/1`（MySQL `TINYINT` 语义），避免驱动把 `true/false` 当字符串。

### 17.6 `text` — 长文本
- **物理列**：`TEXT`（utf8mb4 下约 65535 字节，约 1.6 万汉字）。
- **校验**：**不限长**（`fieldLength` 不参与）。
- **示例**：SQL、JSON、富文本。
- **前端**：`textarea` / 代码编辑器。
- **注意**：更长用 `MEDIUMTEXT`（当前生成器未提供，需要时扩展）。

## 018.归一规则（模板 / 部署 / 设计器保存时）

| 字段 | 归一为 |
|------|--------|
| 基列 `id` / `create_by` / `update_by` | 对应 code，`length=33` |
| 基列 `status` / `dr` | `status`，`length=3` |
| 基列 `create_time` / `update_time` | 对应 code，`length=0` |
| `businessField`（如 `sid`） | `string`，`length=33` |
| `pk_*`（外键/引用列） | `string`，`length=33` |

> 实现：`JulyMetadataTemplateUseCase.baseFieldType/baseLength`（模板）、`JulyMetadataDesignerUseCase.normalizeBusinessField`（设计器）。

## 019.推断来源（探测）

`dataservice011` 探针按结果集列推断 code（`inferFieldData`）：
- 数值型（Oracle `NUMBER` 等）→ `float`
- 字符型（`VARCHAR2(n)` 等）→ `string`（带 length）
- 时间型（`DATE` 等）→ `date`
- 并**追加平台基列**（`id/status/create_by/update_by/create_time/update_time/dr`）。

> 坑（**已修 2026-09-17**）：分页探针的 Oracle 包装会带行号伪列 `klsjnh_rn` —— `BusinessModelingProbe011` 现已在推断时**过滤**该列；别名走 `getColumnLabel`，正常生效。

## 020.运行时校验（`MetadataValueValidator`）

| code | 判定 |
|------|------|
| `int` / `boolean` | 整数或 `true/false/0/1` |
| `float` | `BigDecimal` 可解析 |
| `date` / `create_time` / `update_time` | epoch 毫秒或 `yyyy-MM-dd[ HH:mm[:ss[.SSS]]]` |
| 其余（`string/text/id/status/create_by/update_by`） | `fieldLength>0` 时长度不得超过 |

- **必填**：insert 时 `requiredField=true` 且未提供 → 400；基列 `create_by/update_by/create_time/update_time` **不强制**（平台补默认）。
- 未知 code：`fromString` 返回 null → 生成/校验直接报错。

## 020.1 字典字段（`dictionary011` / `dictionary013` + `param011`）· 草稿

> 核心架构变更：`FieldType011` 增两个业务类型 + `FieldInfo011` 增 `param011`。**命名不缩写**（用全称 `dictionary011` / `dictionary013`）。

### 语义

| 类型 | 含义 | `param011` 存什么 | 选项来源 |
|------|------|-------------------|----------|
| `dictionary011` | **自定义字典**（字段内联选项） | 选项串 `1|是;2|否` | 字段自身 |
| `dictionary013` | **系统字典**（引用 system011 字典） | **字典编码**（如 `SEX`） | `JulyDictionaryUseCase` |

### `param011`（参数011）
- 新增到 `FieldInfo011`（与 `DisplayInfo011.param011` 同名同义：扩展参数）。
- 本期**只加 `param011`**；`param013` 以后再说（不预置空列）。
- 其他字段类型 `param011` 为 null。

### 选项语法（`dictionary011`）
- 形态：`值|标签` 用 `;` 分隔，如 `1|是;2|否`。
- **值 / 标签都不允许包含 `|` 或 `;`**（定案）。
- 值：**语义是 int，但按 string 落列** → 物理列 `VARCHAR(length)`（值存 `"1"`/`"2"`）。
- 解析：按 `;` 拆项、再按第一个 `|` 拆「值/标签」；标签可空？→ 暂定**必填**。

### `dictionary013` 与系统字典（依赖形态 A）
- `param011` = 字典编码；选项/校验复用 system011：
  - 校验值域：`JulyDictionaryUseCase.isValidItem(dictionaryCode, itemCode)`
  - 取标签：`getLabel(dictionaryCode, itemCode)`
  - 选项列表：`selectItemListByType(dictionaryCode, status)`
- 低代码侧**直接注入 `JulyDictionaryUseCase`**（app→app，先例：数据同步复用 `JulyBusinessModelingUseCase`）。
- 前端渲染直接调现有 HTTP `POST /klsjnh/system011/julyDictionary/v1/selectItemListByType`。
- 校验软/硬：**暂缓**（字典查不到的处理后续再定）。

### 物理列
- `dictionary011` / `dictionary013` → `VARCHAR(length)`（缺省口径同 `string`：0/超限→255）。

### 前端渲染
- `dictionary011`：由 `param011` 解析选项 → `select`/`radio`；`dictionary013`：拉系统字典 → `select`/`radio`（缓存）。
- 展示列 `componentType` 建议 `select`/`radio`（见 [016](016.topic-displayinfo.md)）。

### 影响面（实现时）
`FieldType011`（+2）· `JulyMetadataField`(+`param011`) · `JulyMetadataFieldPo` · `july_metadata_field` 加列 · `MetaDTO.fieldData`(+`param011`) · web VO/Converter · `MySqlMetadataDdlGenerator.columnType` · `MetadataValueValidator.checkType` · 040 模板校验（已知类型扩展 + `param011` 透传）· 前端渲染约定 · [011](011.topic-metadata011-system.md) 枚举表。

## 021.使用点与常见坑

**使用点**：DDL 生成（`columnType`）· 模板归一（`baseFieldType/baseLength`）· 设计器（`normalizeBusinessField`）· 运行时校验（`checkType`）· 同步补默认（`defaultValue`）· 前端组件映射（配合展示列 `componentType`）。

**坑**：
1. 业务字段不得用结构列 code（与基列重名 → 大小写不敏感撞键 400）。
2. `dr` 用 `status` 是**有意共用**。
3. `float` 固定 `DECIMAL(18,4)`，金额留意精度。
4. `string` 不给 length → `VARCHAR(255)`；>2000 也回落 255。
5. `id` 是代理主键，别承载业务；业务键用 `businessField`。
6. `boolean` 建议 `0/1` 写入。
