## 011.定位

发布 = 把「元数据定义」变成「物理表」：首次 `CREATE TABLE IF NOT EXISTS`，其后仅 `ALTER ... ADD COLUMN`；同时写**发布快照**、递增**版本**、推进**发布指针**。

## 015.物理表规则

- 表名：`lc_<objectName>`（前缀 `lc_`）。
- 主键：`fieldType=id` 的列；无则自动补 `id VARCHAR(33)`。
- 业务唯一键：`businessField`（如 `sid`）固定 `VARCHAR(33)` + `UNIQUE KEY uk_<table>_<field>`。
- 列类型：`FieldType011` → MySQL（见 [022](015.topic-fieldinfo.md) §15）。
- **DDL 白名单**：首次 `CREATE TABLE IF NOT EXISTS`；其后仅 `ADD COLUMN`；**禁 `DROP`/`DROP COLUMN`/`MODIFY`/`RENAME`**；标识符 `^[A-Za-z_][A-Za-z0-9_]{0,59}$` + 反引号转义。

## 017.发布流程

```
load 聚合 → 表是否存在？
  ├─ 否 → generateCreate（CREATE IF NOT EXISTS）
  └─ 是 → 取缺列 → generateAddColumns（ALTER ADD COLUMN）
→ 执行 DDL（受开关）
→ 写快照 july_metadata_version（payload_json + ddl_text + version）
→ 更新 july_metadata 发布指针（publish_status/version/physical_table）
```
- **开关**：`krt.lowcode.ddl-execute.enabled`（默认 false，生产暗发；dev 开）。
- **幂等**：CREATE IF NOT EXISTS + 仅补缺列；失败可重跑（无 PENDING 断点续做）。
- **版本**：`0.0.1` 起递增（字符串）。
- **不可回滚**：DDL 隐式提交，无事务；只能重跑。

## 023.物理表生命周期策略（2026-09-17 定）

| 事件 | 物理表处置 | 理由 |
|------|------------|------|
| 逻辑删**对象**（`logicDelete`） | **保留** `lc_<object>`（不 DROP、不改名） | DDL 白名单禁 `DROP`/`RENAME`；数据可追溯；误删可救 |
| 逻辑删**数据行** | `dr='1'`（表结构不动） | 逻辑删除 |
| 需要回收物理表 | **人工 / DBA**（或后续"归档"能力） | 自动 DROP 风险过高 |

- 结论：**对象级删除不动物理表**，避免孤儿表被"以为删了"；如需回收走人工。
- 未来可选：加"归档/回收"流程（rename 到 `lc_archive_*` + 定期清理，需 DBA 闸门），当前不做。
