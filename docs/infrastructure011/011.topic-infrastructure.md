# 011 — 项目整体架构选型与设计思路

> 本文档回答两个问题：**为什么选这套技术**，以及**为什么这样分层**。技术栈版本的事实来源是父 `pom.xml`。

## 1. 项目定位

Java17 纯血 DDD 技术底座，以 Maven 多模块交付，供第三方业务系统依赖引用。对外保持稳定契约：路由风格、响应信封、配置结构、公共表结构（见 [016.api-contract.md](../016.api-contract.md)）。

## 2. 技术选型及理由

| 选型 | 版本 | 理由 |
|------|------|------|
| Java | 17 (LTS) | record / sealed / switch 表达式；值对象与聚合的原生表达 |
| Spring Boot | 3.4.5 | jakarta 体系；BOM 统一第三方版本 |
| MyBatis-Plus | 3.5.9 (spring-boot3-starter) | 单表 CRUD 零 SQL；逻辑删除 / 审计填充 / 分页插件内建 |
| MySQL | 8.x | 时间列用 DATETIME（规避 TIMESTAMP 2038 上限） |
| Druid | 1.2.23 | 连接池 + 监控 |
| JJWT | 0.12.6 | 当前 API 形态（0.12.x builder），鉴权过滤器使用 |
| knife4j | 4.5.0 | OpenAPI3 文档 UI，中文注释直出 |
| Lombok | 1.18.36 | PO/VO 样板消除；**domain 层禁用** |

## 3. DDD 分层与依赖铁律

```
web ──► application ──► domain ◄── infrastructure
              │                        │
              └────────► common ◄──────┘   （common 被各层引用，不反向依赖）
```

| 层 | 职责 | 依赖 | 禁止 |
|----|------|------|------|
| common | 跨层契约（枚举/信封/异常/工具） | 无 | 依赖任何业务层 |
| domain | 聚合、值对象、仓储接口、Port | common 共享内核（纯 Java 枚举） | 框架注解、Lombok、PO/Mapper |
| application | 用例编排、事务边界（@Transactional 只在此层） | domain + common | import PO / Mapper |
| infrastructure | PO、Mapper、RepositoryImpl、技术适配 | domain + common | —— |
| web | Controller、统一信封、全局异常、鉴权过滤器 | application + common | 注入 Repository/Mapper，绕过 application |
| app | 唯一 main、装配、profile 配置 | 全部 | 写业务 |

## 4. 核心设计决策

1. **主键由应用侧生成**：用例显式调用 `EntityId.generate()`（32 位无连字符 UUID），BasePo 的 `ASSIGN_UUID` 仅空值兜底。理由：多数据源路由（`krt.ci011`）下每库独立发号会冲突；身份先于落库确定，用例可幂等重试、单次往返返回；v4 UUID 122 位随机，10 亿行碰撞概率 ~10⁻¹⁹，主键约束兜底。
2. **逻辑删除统一走 dr**（'0' 正常 / '1' 已删除），`@TableLogic` 收口，业务代码不物理删；物理删除属基础设施维护动作，必须参数化 SQL 并留日志。
3. **JSON 键 camelCase**，响应信封六键为稳定契约，改动先扩 [016.api-contract.md](../016.api-contract.md)。
4. **实体与 PO 分离**：domain 聚合是纯对象（EntityId/AuditInfo 值对象组合），infrastructure 的 `*Po` 挂 MP 注解，映射代码只存在于 infrastructure。
5. **仓储接口在 domain，实现在 infrastructure**：application/web 只见接口；RepositoryImpl 继承基座家族（`BaseRepository` / `BaseRepository011` / `BaseTreeRepository` / `BaseTreeRepository011`，与 PO 四件套一一对应）。旧版 BaseCrudService011 的 `${sql}` 裸拼属注入漏洞不复用——物理删除仅限维护场景，id 过字符白名单后拼接并留日志。

## 5. 门禁与工具治理

### 5.1 原则

- **两类脚本，职责分开**：检查（gate）与修复（fix）分开；修复**永不**进入 git hooks；
- **规则事实来源**：编码规则统一定义在 [015.coding-standards](../015.coding-standards.md)，tools/ 目录不再单独放规则文档；
- **强制无降级**：AST 检查环境异常 = 门禁失败，不允许跳过；
- **Node.js only**：不保留 PowerShell 一次性迁移脚本。

### 5.2 工具清单（tools/）与操作入口

**根目录 `script011.sh` 是唯一操作入口**（默认 = gate → 版本号 → commit → push；`gate` 仅门禁；`build011` 全量构建安装）。git hooks 不使用——提交一律经 `script011.sh`，门禁在提交前强制执行。

| 文件 | 类型 | 说明 |
|------|------|------|
| `check-klsjnh-standards.mjs` | **检查** | 只读：正则规则 + AST 规则统一入口 |
| `klsjnh-standards-lib.mjs` | 共享 | check 共享逻辑（正则规则） |
| `klsjnh-standards-ast.mjs` | 共享 | tree-sitter AST 检查（funcName / 日志占位 / 命名，环境异常即失败） |

### 5.3 提交门禁

检测失败**不允许 commit / push**：

```bash
node tools/check-klsjnh-standards.mjs .
./script011.sh gate               # 规范检查 + mvn 离线编译
```

### 5.4 违规修复

脚本只查不改：修复由 **AI / 开发者**按 check 输出执行（文件:行 / 违规类型 / 修改说明）；修复类脚本一律不提供。

### 5.5 新增脚本规则

- 只提供**检查类**脚本：必须只读，可进 `script011.sh gate`；
- 修复不做脚本：违规由 AI 按门禁输出修复；
- 一次性迁移/拆分：用完即删，不进仓库长期留存。

### 5.6 环境要求

Node 18+；系统 node_modules 可解析 `tree-sitter`、`tree-sitter-java`（用户级安装：`npm install --save tree-sitter tree-sitter-java`）；缺失时门禁**直接失败**。
