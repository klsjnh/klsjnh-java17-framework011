## 011.定案（不可自行改口径）

1. **删除**三个几乎为空的 Repo 排序层：
   - `BaseRepository011`
   - `BaseTreeRepository011`
   - `BaseTreeSubRepository011`
2. **保留** PO 排序层（列形状）——**本次不合并、不改名**：
   - `BasePo011`（`sort_order`）
   - `TreePo011`（`parent_id` + `sort_order`）
   - 有意分离：**列形状在 PO，查询习惯在 `SortSupport`**（见 §026）
3. **新增**公共件 `SortSupport`（与 `TreeAssembler` / `MasterSubSupport` 同范式：静态工具、无 Spring）。
4. **树默认序**：`BaseTreeRepository.treeWrapper()` 与 `BaseTreeSubRepository.treeWrapper()` 默认改为 `sort_order ASC, id ASC`（经 `SortSupport`）。
5. **无排序树**：降级为「理论格 / 不推荐」——当前无真实表（无 PO `extends TreePo`）；若子类确需仅按 `id` 排，**显式 override** `treeWrapper()`，不得再引入 `*011` Repo 类。并在 `TreePo` Javadoc 写明：默认树序假定存在 `sort_order` 列，无该列必须 override（见 §016 · 013）。
6. **平表有 `sort_order`**：PO 仍 `extends BasePo011`；Repo **只** `extends BaseRepository`（或主子/树链对应基座）；排序**只**在现有 `specWrapper` / 列表 / 分页方法末尾调 `SortSupport.orderBySortThenId(wrapper)`。**禁止**再造 `BaseRepository011`，**禁止**在业务仓储上再包装一层 `sortedWrapper()` 式半截 011。
7. **命名**：不新增 `BaseRepository021` 之类；`BaseMasterSubRepository011` **本次不改名**（另案）。`JulySyncRuleRepositoryImpl` 等已挂主子基座的**不动继承关系**。

## 013.背景（为何改）

| 类 | 现状（2026-09-22 核对） | 问题 |
|----|-------------------------|------|
| `BaseRepository011` | 仅 `sortedWrapper()` 两行 orderBy；**2 个**继承方（见下） | 空壳；且与「排序应收公共件」新口径冲突 |
| `BaseTreeRepository011` | 仅 override `treeWrapper` → sort_order/id | 菜单/组织在用，但子类又重复写同一 `treeWrapper` |
| `BaseTreeSubRepository011` | 同上 | 仅 AI 域树在用；增量同样只有排序 |

**`BaseRepository011` 继承方（必须回收，不是「预期无」）**：

| 类 | 说明 |
|----|------|
| `JulyDatasourceRepositoryImpl` | 上一轮为对齐旧矩阵「有 sort_order ⇒ BaseRepository011」临时迁入；**本方案反向回收** → `BaseRepository` |
| `JulySyncRuleColumnRepositoryImpl` | 同上；子表仍 `BasePo011` + `MasterLinked`，Repo → `BaseRepository` |

> `sortedWrapper()` **方法调用**仍可为 0；继承方是 2——执行 AI **不得跳过**这两处。

结论：**排序是列约定 + 查询习惯，不是独立仓储生命周期。** 继承轴为空壳；应收到组合公共件。

### 011.新增 `SortSupport`

路径：

`java17-infrastructure011/src/main/java/com/klsjnh/infrastructure/persistence/support/SortSupport.java`

要求：

- `final` 类 + private 构造
- 英文 Javadoc + 本项目文件头块（见 `016.coding-standards`）
- 提供：

```java
/**
 * Apply default business sort: sort_order ASC, then id ASC.
 * Prefer this in business RepositoryImpl (specWrapper / list / page).
 */
public static <T> QueryWrapper<T> orderBySortThenId(QueryWrapper<T> wrapper)

/**
 * New empty wrapper already ordered by sort_order, id.
 * Intended for repository-base treeWrapper only; business repos should use
 * {@link #orderBySortThenId(QueryWrapper)} on their existing wrappers —
 * do not reintroduce a per-repo sortedWrapper() habit.
 */
public static <T> QueryWrapper<T> sortedWrapper()
```

- 列名写死 `"sort_order"` / `"id"`
- **禁止**依赖 Spring / 具体业务 PO

### 013.改树基座默认序 + TreePo 警告

1. `BaseTreeRepository.treeWrapper()`：`return SortSupport.sortedWrapper();`
2. `BaseTreeSubRepository.treeWrapper()`：同上
3. 两处 Javadoc：默认 `sort_order, id`；无 `sort_order` 列必须 override
4. **`TreePo` 类 Javadoc 补一句**：本基座默认树序假定表含 `sort_order`；无该列的理论形态须在仓储 override `treeWrapper`，否则 SQL 失败。`TreePo011` 为推荐树 PO

### 016.手写 `orderByAsc("sort_order")` 改写判据（C2 定案）

全仓 `*RepositoryImpl` 约 21 处。**必须改 / 可留**如下，避免演成大重构：

| 判据 | 动作 |
|------|------|
| A. 独立 wrapper 仅做 `orderByAsc("sort_order").orderByAsc("id")` | **必须**改为 `SortSupport.sortedWrapper()` 或 `orderBySortThenId(new QueryWrapper<>())` |
| B. 带业务条件的链式（`eq`/`like` 后接 orderBy） | **必须**只换排序段：条件链保留；末尾 `SortSupport.orderBySortThenId(wrapper)`（可拆成两句） |
| C. 与拟议默认相同的 `treeWrapper` override | **必须删** override |
| D. 非 `QueryWrapper`（原生 SQL / 其它） | **允许留**；汇报 §021 列出路径 |
| E. 改完后仍残留的 `orderByAsc("sort_order")` | **允许留 0 处为佳**；若因 D 残留，汇报须列全；**验收不因「仍有 orderBy 字面量」失败，但因「A/B/C 未改」失败** |

**禁止**：为「换 SortSupport」去重构无关查询逻辑、改 domain 接口、改 VO。
