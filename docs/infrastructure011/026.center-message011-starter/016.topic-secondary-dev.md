## 013.新出站渠道（最常见）

**实现 `MessageChannelPort`，注册为 bean 即接入**（`MessageChannelRegistry` List 自动收编；管理面建渠道行、config JSON 填参数——**零配置代码**）：

```java
@Component
public class DingTalkMessageChannel implements MessageChannelPort {

    // 渠道 code：开放字符串（MessageProviderTypes011 增量常量），禁封闭枚举做路由键
    // config JSON 由本类 parseConfig 解析（endpoint / token 等），解析失败要有日志
    // HTTP 统一走 common.util.HttpUtil011；响应体大小时刻设上限
    // 返回 MessageResult（成功 / 失败 + 渠道侧回执），记录由 use case 落表
}
```

**纪律与参照**：

- 参照物：`WebhookMessageChannel`（HTTP 型，**9 个转义回归单测**是渠道测试样板）/ `InAppMessageChannel`（落库型）；
- 单测放本模块 `src/test`（Mockito，不起 Spring 上下文）；
- gate 强制项：文件头块 / Javadoc 英文 / funcName 日志占位符 / `*011` 命名。

## 015.新入站源

1. 实现 `MessageInboundPort`（接入源：webhook 回调、MQ 轮询、IM 机器人…）；
2. 实现 `InboundMessageListener`（消费分发的业务侧）；
3. 入站去重：以幂等键走唯一约束兜底，业务预检查仅作友好提示；
4. 接收记录统一落 `july_inbound_message`，排查以表为准。

## 018.管理面 / 表结构扩展

- 六表任何变更走 [july_center_message.sql](../../sql/july_center_message.sql)（DDL 单一真源）；
- 字段新增全链路：PO（`pkMt` 主链纪律）→ Mapper → RepositoryImpl → UseCase → VO（`*Vo011`）→ Converter；
- 出入两套**成对改**：历史教训是克隆家族"一处修另一处漏"——任何一侧的行为修正，先 grep 另一侧（详见 017 技术债：克隆家族收敛）。

## 021.红线（本中心特别三条）

1. **渠道 code 开放字符串 + 注册表**——禁止封闭枚举做路由键（扩展不改底座是本中心的存在理由）；
2. **渠道实现无状态**——差异化全在渠道表 config JSON；config 解析失败要有日志（当前静默默认值已登记 017 债项）；
3. **记录先行**——发送 / 接收先落记录再回填结果；禁止"发送成功才落库"。
