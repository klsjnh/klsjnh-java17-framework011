# 017 — 技术债红线（Tech-Debt Redlines）

> **定位**：只回答一件事 —— **什么绝对不许做**。每条都对应一次真实踩坑或事故级约束，附「违反的后果」。
> **与 [016.coding-standards.md](016.coding-standards.md) 的分工（不重复）**：016 讲「怎么写才算合格」（分层 / 命名 / 风格 / 门禁映射与规则名）；本文讲「红线与后果」。**写法细节一律引 016 的编号章节，本文不复制正文。**
> **准入判据**：写进本文的条目必须满足「**违反即产生技术债、审计缺口或线上事故**」；否则归 016。
> **强制方式标注**：【AST】/【正则】= 机检（规则名对照 016 **§11** 门禁映射）·【评审】= 人工 ·【卫兵】= 启动期直接抛异常熔断。

## 011.分层红线（DDD）

### 011.domain 必须纯净

- 只许纯 Java + `record`；**禁 Lombok、禁一切框架注解**（Spring / MyBatis-Plus）。
- 只可依赖 common 的**纯 Java 共享内核**（枚举 / 工具类，如 `Status011` / `StringUtil011`）；**共享内核类本身也必须零框架依赖** —— 否则纯净性从 common 处反向破口。
- **后果**：domain 一旦被框架注解污染，聚合就绑死在框架生命周期上，换 ORM / 换框架 = 重写领域层。

### 013.`@Transactional` 只在 application

- 事务边界是**用例边界**，不是仓储边界。infrastructure / web / domain 一律不出现。
- **后果**：仓储自带事务会切碎用例的原子性 —— 一次用例的多次写各成一事务，中间失败留下脏数据。
- **明示例外（2026-09-22 审核）**：`infrastructure.iam.user.UserAuditRecorder#record` 允许 `@Transactional(REQUIRES_NEW)` —— 审计行必须在业务事务回滚后仍可独立落库；**不得**把该例外扩到其它 infra 类。

### 015.PO 只活在 infrastructure

- application / web **不 import 任何 `*Po` / `*Mapper`**。
- **后果**：PO 是数据库形状（含 `dr` / `sort_order` / `pkMt`），一旦上浮到 web，DB 改列就变成对外契约的破坏性变更。

### 016.注入与实现方向

- Controller 只注入 application 服务；RepositoryImpl 实现 domain 仓储接口（**接口在 domain、实现在 infrastructure**）。
- 一律**构造器注入**，不用字段注入。
- **后果**：反向依赖 = 领域层依赖基础设施，DDD 分层退化为目录装饰。
- **明示例外（2026-09-22 审核）**：Quartz `Job` 实现类（现仅 `SchedulerHandlerJob`）允许字段 `@Autowired` —— Spring Boot 默认 `AutowiringSpringBeanJobFactory` 以无参构造实例后再注入；强行构造器注入会破坏调度装配。

## 013.持久化红线

### 011.主键必须由应用侧生成

- 用例显式调用 `EntityId.generate()`（32 位无连字符 UUID，**列宽 33**）；`BasePo` 的 `ASSIGN_UUID` **仅空值兜底**，不是主生成路径。
- **不许**依赖数据库自增、序列或逐库发号。
- **后果**：多数据源（`krt.ci011`）下每库独立发号必然冲突；身份先于落库确定，用例才能幂等重试、单次往返返回。
- 引：[infrastructure011/011.topic-infrastructure.md](infrastructure011/011.topic-infrastructure.md) §4 决策 1。

### 013.逻辑删除一律走 `dr`，不物理删

- `@TableLogic(value = "0", delval = "1")` 收口；业务代码**禁止物理删**。
- **后果**：物理删 = 审计链断裂 + 主子表悬挂 + 不可回滚。物理删除只属基础设施维护动作（见本文 016.物理删除仅限维护场景）。

### 015.审计四列必须自动填充

- create_by / update_by / create_time / update_time 由 `AuditMetaObjectHandler` 填充；操作人读请求作用域属性 `FrameConst011.OPERATOR_ID`（`krt.operatorId`，由 `GlobalAuthFilter` 校验 JWT 后写入）。
- **禁止**业务代码手写 `setCreateTime` / `setCreateBy`；**禁止**引入 `OperatorContext` 式全局上下文 —— ThreadLocal 漏清理 = 跨请求串号。
- 时间列直接取当前时间；操作人列无值即视为未鉴权路径。

### 016.树与排序约定

- 树形根节点 `parent_id` 用**空串**，不是 `null` —— `null` 在 `parent_id = ''` 的查询里永远匹配不上。
- `sort_order` 越小越靠前，**默认 9999 由建表默认值兜底**，Java 侧不设初值 —— 否则「未指定」与「显式指定 9999」无法区分。

### 017.唯一性以数据库索引为准

- 业务层唯一性断言**只是友好预检**，真正的保证是**数据库唯一索引**。
- **后果**：并发下「先查后插」必然穿透。

### 018.禁魔法值

- 状态 / 删除标记的比较一律走枚举（`Status011.ENABLED` 等），代码中不得散落 `'0'` / `'1'` 字面量（DDL 注释除外）。
- 引：016 §7。

## 015.接口契约红线

### 011.POST 为主、禁路径参数

- `@*Mapping` **禁止 `/{param}`**；点查用 GET + query string，写动作用 POST + JSON body。
- **后果**：路径参数把 id 写进路由，网关缓存 / 重试 / 日志脱敏全部失效；方法语义谎报（点查用 POST）会让本可自愈的失败变成必须上报用户的失败。
- 引：016 §6.1 / §6.2【正则 `api-url` / `api-method`】。

### 013.信封六键与 camelCase 不可变

- `Response011` 六键（statusCode / message / errorMessage / timestamp / traceId / data）**不许改名、删键、重排**；JSON 键一律 camelCase。
- 新增状态码**先扩契约文档**（[013.api-contract.md](013.api-contract.md)），再加常量。
- **契约的事实来源是源码，Swagger 输出只是视图** —— 已知缺口见 [019.backend-api-review.md](019.backend-api-review.md)。

### 015.删除动作分层，不合并不重载

- `logicDelete`（收 `IdVo011`，不存在抛 `recordNotFound`）与 `logicDeleteBatch`（收 `IdsVo011`，返回 `BatchDeleteResultVo011`）**必须是两个动作**。
- `delete` 一词已被物理删除占用，逻辑删除**必须**保留 `logicDelete` 词根。
- 引：016 §6.3。

### 016.入参必须具名 VO

- 请求载荷一律 `*Vo011`，**不许裸集合 / 裸 Map** —— 无法演进、Swagger 无 schema 名、参数校验报错无法定位到具体字段。
- 引：016 §6.3。

## 016.安全与出站红线

### 011.堆栈 / SQL 不出站

- 异常响应只回客户端**安全提示**；`errorMessage` **仅 debug 态填充**，生产为空。
- **后果**：SQL 片段 / 表名 / 堆栈一旦出站即为信息泄露面。

### 013.密钥不落提交

- `application.yml` 公共结构**无密钥**；数据源与 `krt` 凭据落在入库的 `application-development.yml`；生产 secret 经环境变量注入。
- **后果**：密钥进 git = 必须轮换的历史泄露，删不掉。

### 015.启动卫兵（配置组合熔断）

以下组合**启动即抛异常**，不允许「跑起来再说」：

| 组合 | 熔断方式 | 实现 |
|------|----------|------|
| `krt.status=debug` + `production` profile | `IllegalStateException` | `KrtSecurityConfig011` |
| `production` profile 下 `krt.jwt.secret` 缺失 | `IllegalStateException` | `KrtSecurityConfig011` |
| 免密登录在 production | `BusinessException.unauthorized` | `RuntimeStatusPort` / `JulyUserUseCase` |

- **后果**：这三条任一条被绕过，等于生产环境开了后门。

### 016.物理删除仅限维护场景

- id 必须过**字符白名单**后再拼接 SQL，且**必须留日志**。
- 旧版 `BaseCrudService011` 的 `${sql}` 裸拼属注入漏洞，**不复用**（见本文 019.历史债）。

## 017.构建与工具红线

### 011.版本统一在父 pom

- 版本一律由父 `pom.xml` 的 `dependencyManagement` 管理，**子模块不许自带 `<version>`**。
- **后果**：子模块自带版本 = 同一依赖多版本共存，运行期行为随「谁先加载」漂移。

### 013.禁绕过提交入口

- 写操作（add / commit / push）**只能经 `script011.sh`**；禁原生 `git` 提交；**不设 git hooks**（门禁在提交脚本内先行执行）。
- 引：[011.agreements.md](011.agreements.md) §011.015。

### 015.脚本只查不改

- `tools/` 下的 check 脚本**只读**，输出三要素（文件:行 / 违规类型 / 修改说明）后由人修；**修复类脚本永不进 git hooks**。
- **后果**：自动「修复」会掩盖违规模式，把门禁变成静默改写。

## 018.注释与文档红线

- **文件头块**：`package` 与头块之间、头块 `*/` 与 `import` 之间各空一行；history 行写**小写描述**，禁写类名。引 016 §1【`file-header`】。
- **Javadoc 一律英文**；字段用单行 `/** ... */`；**中文描述只放 web 层 VO 的 `@Schema` 与 DDL 注释**；**实体 / PO 层不挂 `@Schema`**。引 016 §2。
- **`funcName` 模式**：操作方法开头 `String funcName = "<操作名>"`，错误消息与日志复用之；值必须**小写空格分隔**（禁连字符 / 下划线 / 大写）。引 016 §3。
- **日志**一律 `{}` 占位符、**禁字符串拼接**（跨行也拦）；首占位符恒为 `funcName`。引 016 §4【`log-concat` / `log-funcname`】。
- 文档引用一律**用编号指路**，且必须指向**当期编号** —— 改名后残留的旧编号引用本身就是技术债（实例见本文 019 末行）。
