### 011.archive011/（归档规则）

- 每日工作结束后，将精简工作日志记录至 `docs/{YYYY-MM-DD}.md`，原始对话整理至 `docs/{YYYY-MM-DD}-chat.md`
- 每日首个任务开始前，将历史日志自动归档至 `docs/archive011/` 目录下，保证 docs/ 根路径仅存留当天文件
- `requirement011/`、`requirement013/`、`sql/` 与 `infrastructure011/` 为常驻知识库，禁止归档

### 015.requirement011/ & requirement013/（业务设计 → 技术方案）

两目录按**设计推进阶段**递进，同一主题**同编号贯穿**：

- `requirement011/`：**业务设计与业务要求**（业务视角 · 分主题）—— 业务侧设计输入，含用户原始诉求、业务规则与边界
- `requirement013/`：**技术方案** —— 双源合流的**唯一落点**：合入 `requirement011/`（业务视角）与 `infrastructure011/`（架构视角），给出可实施的技术方案、业务规则、约束与错误码、修订日志

> **双源归口**：`infrastructure011/`（整体底层架构设计）与 `requirement011/`（业务设计）**同为设计输入、两个视角**，二者在 `requirement013/`（技术方案）收敛为唯一落点。
> **不跳层（铁律）**：任何主题都**逐层**推进 —— 源（`infrastructure011/` 或 `requirement011/`）→ `requirement013/`（技术方案）。**禁止跨层下放**；架构主题（`config` / `persistence` 等）同样必须经 `requirement013`。

### 016.编号规则（全局序列）

编号（`{编号}`）是**全项目共享的一支序列**，与所在目录**无绑定关系** —— 同一个号可以作目录名、主题文件名，也可以作文档内小节号。

- **分配规则（两条禁忌）**：从 `011` 起**递增分配**，**跳过含数字 `4` 的号**（`014 / 024 / 034 / 040–049 / 140–149 …`），并**跳过 `012`**；其余**连号不留空**
- **序列取值**：`011 / 013 / 015 / 016 / 017 / 018 / 019 / 020 / 021 / 022 / 023 / 025 / 026 / 027 / 028 / 029 / 030 / …`
  - `011 / 013` 同时是**两个阶段目录的保留号**（`requirement011 / requirement013`），与全局序列同源 —— `012`（禁忌号）与 `014`（含 `4`）自然空出，**并非步长为 2**
  - `013.project-info` / `015.coding-standards` / `016.api-contract` 属顶层常驻文档，同样占用全局号
- **不复用、不回收**：一个号一经分配即永久占用 —— 文件改名、移出、归档、撤销均**不释放**该号
- **文档内小节号（分层独立起编）**：**每一级各自**从 `011` 起，按**同一规则**递增（跳 `012` 与含 `4` 的号）；**同级内递增**，不跨级连续
  - **子节序列独立**，不占用父级序列 —— 故 **父级恒为连续序列、不会因嵌套而断档**
  - 父级与其首个子节**可以同号**（例：`## 011.文档体系与目录结构` 下挂 `### 011.归档规则` … `### 016.编号规则`）—— 层级不同，不算冲突
  - 跨节引用**连父级一起写**（如 `§011 · 016`、`§015 · 017`），仅写 `§011` 会与父节歧义
- **同一主题同编号贯穿**：`{编号}.topic-{主题}.md`（主题 kebab-case 英文，如 `021.topic-july-scheduler.md`）在 `requirement011 / 013` 两目录**同名**（见 `§011 · 015`）
- **编号 ≠ 层级（铁律）**：小节号写作 `013` / `015` **不代表**该文档已跨到 `requirement013` 层；层级**只由内容决定**，仍受 `§011 · 015`「不跳层」约束
